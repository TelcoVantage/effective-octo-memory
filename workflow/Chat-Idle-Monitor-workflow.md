# Architect workflow: `Chat Idle Monitor`

This workflow is the "brain" of the solution. One instance runs per chat/messaging
interaction from the moment an agent is assigned to it. Every minute it checks who
sent the last message and when, and it writes the result to participant data on the
customer participant. The agent script (`script/Chat-Idle-Alert.script`) only reads
those three attributes:

| Participant attribute | Meaning |
|---|---|
| `IdleAlert`   | `"1"` while an alert is active, `"0"` when it is cleared |
| `IdleMinutes` | Minutes since the agent's last activity (last message sent, or connect time) |
| `IdleSeq`     | Counter incremented on **every** change. The script reacts only when it changes. |

## Fastest route: import the ready-made file

`workflow/Chat Idle Monitor.i3WorkFlow` is a complete export in Architect's own format
(generated by `tools/build_workflow.py`; `Chat Idle Monitor.decoded.json` next to it is the
same flow as readable JSON).

1. Import the two data actions first (section 0) so Architect can resolve them **by name**.
2. Architect > Flows > Workflow > **Add**, name it `Chat Idle Monitor`, open it.
3. Flow menu (top-left) > **Import**, choose the `.i3WorkFlow` file, wait for validation.
4. Open the two *Call Data Action* steps and confirm they point at the imported data actions
   (if your org shows them unresolved, re-select them from the dropdown; the input/output
   mappings are kept). If you prefer, regenerate the file with your ids baked in:
   `python3 tools/build_workflow.py --get-action-id custom_-_… --set-action-id custom_-_…`
5. Adjust `State.ThresholdMinutes` / `State.RepeatEveryMinutes` / `State.OnlyWhenCustomerWaiting`
   under Resources > Data if needed, then **Save** and **Publish**.
6. Create the trigger (section 3), then enable it.

The manual build below produces the identical flow and doubles as the documentation of
what the imported file does. No Archy, Terraform or external services are needed.

---

## 0. Prerequisites

1. Integration **Genesys Cloud Data Actions** is active (Admin > Integrations).
   Its OAuth client's role must be allowed to read conversations and edit participant
   attributes. Check the "Required permissions" box in the API Explorer for
   `GET /api/v2/conversations/messages/{conversationId}` and
   `PATCH /api/v2/conversations/{conversationId}/participants/{participantId}/attributes`
   and add them to that role (typically *Conversation > Communication > View* and
   *Conversation > Communication > Edit*).
2. Import the two data actions from `data-actions/` (Admin > Integrations > Actions >
   **Import**), then **Save & Publish** each. Test the GET one with a real conversation ID
   from a finished web messaging interaction and confirm the arrays come back populated.

## 1. Create the workflow

Architect > Flows > **Workflow** > Add. Name: `Chat Idle Monitor`.

### 1.1 Flow-level **input** variables (names must match the trigger event exactly)

| Name | Type | Input |
|---|---|---|
| `Flow.conversationId` | String | yes |
| `Flow.participantId`  | String | yes |
| `Flow.userId`         | String | yes |
| `Flow.queueId`        | String | yes |
| `Flow.mediaType`      | String | yes |

### 1.2 State variables (settings you tune)

Workflows run inside a *State*, so its local variables use the `State.` prefix.

| Name | Type | Default | Purpose |
|---|---|---|---|
| `State.ThresholdMinutes`        | Integer | `3`    | Minutes of agent silence before the first alert |
| `State.RepeatEveryMinutes`      | Integer | `3`    | Re-alert interval while still idle (`0` = alert once) |
| `State.OnlyWhenCustomerWaiting` | Boolean | `true` | Alert only if the customer's last message is newer than the agent's (recommended) |
| `State.MaxPolls`                | Integer | `240`  | Safety cap: 240 one-minute polls = 4 hours per interaction |

### 1.3 State working variables

`State.Seq` (Integer, 0), `State.AlertActive` (Boolean, false), `State.LastAlertMinutes` (Integer, 0),
`State.Failures` (Integer, 0), `State.AgentIndex` (Integer), `State.AgentConnectedTime` (DateTime),
`State.LastAgentMsg` (DateTime), `State.LastCustomerMsg` (DateTime), `State.IdleSince` (DateTime),
`State.IdleMinutes` (Integer), `State.HasAgentMsg` (Boolean), `State.HasCustomerMsg` (Boolean),
`State.CustomerWaiting` (Boolean), `State.CustomerParticipantId` (String), `State.PollIndex` (Integer)

Data-action outputs (String **collections**):
`State.customerParticipantIds`, `State.customerMessageTimes`, `State.agentMessageTimes`,
`State.connectedAgentUserIds`, `State.connectedAgentTimes`, `State.alertingAgentUserIds`

## 2. Flow logic

```
Start
└─ Loop  "Poll"           (Loop count: expression State.MaxPolls, index: State.PollIndex)
   ├─ Wait                 (Duration literal: 0 days 0 hours 1 minute 0 seconds)
   ├─ Call Data Action     "GC - Get Message Conversation Activity"
   │     input  conversationId = Flow.conversationId
   │     outputs -> the six State.* collections above
   │     Failure path: Update Data State.Failures = State.Failures + 1
   │                   Decision State.Failures >= 5 ? Exit Loop : Next Loop
   ├─ Update Data          State.AgentIndex = FindFirst(State.connectedAgentUserIds, Flow.userId)
   ├─ Decision  "Agent still connected?"   State.AgentIndex >= 0
   │     No  ─ Decision "Still alerting?"  FindFirst(State.alertingAgentUserIds, Flow.userId) >= 0
   │             Yes -> Next Loop        (agent has not accepted yet)
   │             No  -> Exit Loop        (agent disconnected / transferred / chat ended)
   │     Yes ─ continue
   ├─ Update Data  "Compute activity"   (one Update Data action, statements in this order)
   │     State.AgentConnectedTime    = ToDateTime(State.connectedAgentTimes[State.AgentIndex])
   │     State.HasAgentMsg           = Count(State.agentMessageTimes) > 0
   │     State.HasCustomerMsg        = Count(State.customerMessageTimes) > 0
   │     State.LastAgentMsg          = If(State.HasAgentMsg,
   │                                     ToDateTime(State.agentMessageTimes[Count(State.agentMessageTimes) - 1]),
   │                                     State.AgentConnectedTime)
   │     State.LastCustomerMsg       = If(State.HasCustomerMsg,
   │                                     ToDateTime(State.customerMessageTimes[Count(State.customerMessageTimes) - 1]),
   │                                     State.AgentConnectedTime)
   │     State.IdleSince             = If(State.LastAgentMsg > State.AgentConnectedTime, State.LastAgentMsg, State.AgentConnectedTime)
   │     State.IdleMinutes           = ToInt(ToInt(DateTimeDiff(GetCurrentDateTimeUtc(), State.IdleSince)) / 60000)
   │     State.CustomerWaiting       = State.HasCustomerMsg and (not State.HasAgentMsg or State.LastCustomerMsg > State.LastAgentMsg)
   │     State.CustomerParticipantId = If(Count(State.customerParticipantIds) > 0, State.customerParticipantIds[0], "")
   ├─ Decision  "Idle?"
   │     (State.IdleMinutes >= State.ThresholdMinutes) and (State.CustomerWaiting or not State.OnlyWhenCustomerWaiting)
   │     Yes ─ Decision "Raise / repeat?"
   │     │       not State.AlertActive or (State.RepeatEveryMinutes > 0 and State.IdleMinutes - State.LastAlertMinutes >= State.RepeatEveryMinutes)
   │     │       Yes ─ Update Data   State.Seq = State.Seq + 1 ; State.AlertActive = true ; State.LastAlertMinutes = State.IdleMinutes
   │     │             Call Data Action "GC - Set Idle Alert Attributes"
   │     │                 conversationId = Flow.conversationId
   │     │                 participantId  = State.CustomerParticipantId
   │     │                 idleAlert      = "1"
   │     │                 idleMinutes    = ToString(State.IdleMinutes)
   │     │                 idleSeq        = ToString(State.Seq)
   │     │       No  ─ (nothing)
   │     No  ─ Decision "Clear active alert?"   State.AlertActive
   │             Yes ─ Update Data   State.Seq = State.Seq + 1 ; State.AlertActive = false ; State.LastAlertMinutes = 0
   │                   Call Data Action "GC - Set Idle Alert Attributes"  (same inputs, idleAlert = "0")
   │             No  ─ (nothing)
   └─ (loop continues)
End Workflow
```

Notes on expressions:

* The Loop count is the *expression* `State.MaxPolls`; the literal editor caps at 99, an expression does not.
* `FindFirst(collection, value)` returns `-1` when not found; `Count()` and `[index]` work on collections.
* `DateTimeDiff(a, b)` returns a Duration; `ToInt(duration)` gives milliseconds, hence `/ 60000`.
  If your editor flags `DateTimeDiff`, use `ToInt(GetCurrentDateTimeUtc() - State.IdleSince)` instead.
* The data action returns the last 30 message timestamps per side (`messages[-30:]`). The
  conversation API lists messages in chronological order, so the last element is the newest.
* Attribute values are strings. The script compares `IdleAlert` to the text `1`.

## 3. Trigger (Admin > Triggers > Add)

| Field | Value |
|---|---|
| Name | `Chat Idle Monitor - agent assigned` |
| Topic | `v2.detail.events.conversation.{id}.user.start` |
| Target | Workflow `Chat Idle Monitor` |
| Data format | **TopLevelPrimitives** (so `conversationId`, `participantId`, `userId`, `queueId`, `mediaType` arrive as flow inputs) |
| Match criteria | `mediaType` **Equal** `MESSAGE` — open the topic's schema in the trigger UI and copy the exact enum spelling it shows |
| Optional criteria | `queueId` **In** `[<your chat queue IDs>]` to limit it to chat queues |

If you still run legacy ACD web chat (media type `CHAT`), create a second trigger with
`mediaType` Equal `CHAT` and point it at a copy of the workflow whose GET data action calls
`/api/v2/conversations/chats/${input.conversationId}/messages` instead (that API returns
`entities[].utcTime` and `entities[].sender.id`; filter by the sender participant purpose).

The same trigger as an API payload is in `trigger/Chat Idle Monitor.trigger.json`. To create it
without the UI, open Genesys Cloud **Developer Tools > API Explorer** (Admin > Integrations is
not needed), choose `POST /api/v2/processautomation/triggers`, paste the file, replace the
`target.id` placeholder with the published workflow's id (Architect shows it in the URL), and
run it. The file is created with `"enabled": false`; flip it to `true` (or `PATCH` it) once the
workflow is published and the script is assigned to the queue.

Enable the trigger last, after the workflow is published and the script is assigned to the queue.

## 4. Optional escalation

Inside the "Raise / repeat?" Yes branch add a Decision `State.Seq >= 3`. On Yes, add a
**Send Notification** action (email or group chat to the team lead) with
`Flow.conversationId` and `State.IdleMinutes` in the body. That action is capped at three
sends per workflow run, so keep it to the third alert and above.
